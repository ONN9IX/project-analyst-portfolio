# Project Charter — аналитический кейс ПРОМАКС

**Документ аналитика, не утверждённый оригинальной командой проекта.** Создан 13.10.2026 на основе публичного Smart Garden. Слова «цель», «риски» и «критерии» ниже относятся к **аналитическому кейсу**, а не заменяют продуктовые контракты исходного репозитория.

## 1. Проблема

Открытые Issues, история Pull Requests и README позволяют увидеть технические изменения, но сами по себе не являются удобным отчётом руководителю: без отдельной обработки трудно отделить выполненную работу от новых запросов, найти активные риски и понять ограничения данных.

## 2. Цель аналитического кейса

Создать воспроизводимый набор проектных показателей, отчётов и документов для Junior Project Analyst на одном подтверждаемом репозитории.

## 3. Входные данные

- GitHub Issues, включая даты создания/закрытия, статус, назначенного исполнителя и ссылку.
- GitHub Pull Requests: создание, merge и статус.
- Продуктовое README как справка о техническом MVP и ограничениях.

## 4. В границах

- Разделять задачи и Pull Requests.
- Рассчитывать текущие для выбранного среза статусы и динамику.
- Описывать источники, допущения и управленческие риски.
- Готовить Excel-дашборд, SQL-запросы и статусный отчёт.

## 5. Вне границ

- Работа с кодом или закрытыми данными исходного Smart Garden.
- Изменение или приоритизация реального backlog без решения владельца.
- Расчёт заработной платы, коммерческой себестоимости, EVM, выполнения сроков без исходного baseline.
- Юридическая оценка соответствия 152-ФЗ или допуск к обработке данных детей.

## 6. Заинтересованные стороны (аналитическая модель)

- Владелец продукта — потребитель статуса и решений.
- Участники разработки — источники статусов и контекста задач.
- Потенциальные пилотные организации — будущие потребители продукта.
- Проверяющий кейс / интервьюер — оценка навыков анализа, а не реальный заказчик.

## 7. Критерии готовности кейса

1. CSV-данные со ссылками на каждую Issue/PR.
2. Итоговые цифры подтверждаются Python-тестами и Excel-формулами.
3. Есть понятные управленческие выводы без ложного процента готовности.
4. SQL-запросы работают с двумя раздельными сущностями.
5. Явно перечислены отсутствующие данные и экспертные предположения.
