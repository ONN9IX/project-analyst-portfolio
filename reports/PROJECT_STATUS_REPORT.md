## Интерпретация

Высокая доля закрытых Issues отражает **статус GitHub-реестра**, а не процент готовности продукта. Одна Issue может быть маленькой технической задачей, а другая — отдельным крупным этапом. Назначения (`assignee`) также не равны фактически затраченным часам.

В README исходного проекта технический MVP описан как сформированный; стадии 1–6 технически приняты. При этом проект **не заявлен как production-ready для реальных персональных данных**.

## Следующий управленческий шаг (рекомендация аналитика, не официальное решение команды)

1. Перед пилотом отдельно утвердить **go/no-go** по безопасности и персональным данным.
2. Открытые направления разбить на небольшие проверяемые поставки; зафиксировать владельца и критерии готовности.
3. Начать собирать реальные плановые даты, фактические трудозатраты, оценки сложности и причины блокировок: сейчас их недостаточно для честного EVM, SPI/CPI и оценки исполнения сроков.

## Ограничения

- API-срез на дату 13.10.2026; изменения позже не отражены.
- В данных нет согласованного baseline по срокам, бюджету и ресурсам, поэтому **не рассчитаны** план-факт бюджета, стоимость, velocity и производительность отдельных людей.
- Поле даты фиксирует календарный день, поэтому разницу между открытием и закрытием Issue нельзя считать реальной трудоёмкостью.
- Названия добавлены только для избранных Issues; для остальных первоисточник открывается по `source_url`.
